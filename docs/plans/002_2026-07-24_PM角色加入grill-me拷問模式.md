# 002 ─ PM 角色加入 grill-me 拷問模式

## 〇、背景:grill-me 是什麼

「grill-me」是 Claude Code 社群廣為流傳的一個 skill(Matt Pocock 等人的版本最有名,
Boris Cherny 也公開推薦過同類手法):在動工前,AI 對使用者進行**蘇格拉底式的連環拷問**——
一次只問一個尖銳問題、附上自己的建議答案讓使用者反應、對薄弱理由 push back、
把隱藏假設全部攤到檯面上,直到整個決策樹每一條分支都被走完,才進入實作。
目的是消除「你以為你想清楚了、其實沒有」的專案不確定性。

本需求:把這套拷問方法**內建進本模板的 PM 角色**(階段 1 需求討論),
讓 PM 不只是被動釐清需求,而是有一套系統化的逼問流程。

## 一、這次要做什麼

1. **在 `CLAUDE.md` 的「階段 1 ─ 需求討論」加入「grill-me 拷問模式」小節**,內容(改寫自原版 skill,收斂成條列):
   - **啟動時機(雙軌)**:
     - 使用者明說「grill me」/「烤我」/「拷問我」→ 必須進入完整拷問模式。
     - PM 判斷需求重大或模糊(範圍不清、影響既有功能、成本高)→ **主動建議**進入拷問模式,由使用者決定要不要;小需求不強制,避免煩人。
   - **拷問流程**:
     1. 先靜默建立這個需求的**決策樹**:範圍界線、相依關係、失敗模式、被捨棄的替代方案、成功標準、可回退性、維護歸屬。
     2. **一次只問一個問題**,並附上 PM 自己的建議答案(strawman)讓使用者直接反應,不出是非題以外的開放大哉問轟炸。
     3. **能自己查的不問**:先讀 code / `docs/` 文件找答案,只問文件裡沒有的。
     4. **一條線追到底**才換下一條;對「應該沒問題吧」這類薄弱理由要 push back;把使用者沒說出口的隱藏假設明講出來請他確認。
     5. 使用者可隨時喊「夠了」提前收尾。
   - **收尾產出**:拷問結束時輸出四段總結——「已確認的決策 / 過程中改變的想法 / 仍未決的問題 / 浮現的新風險」——這份總結直接作為階段 2 規劃書的素材;關鍵取捨照舊在階段 3 確認後寫入 `docs/DECISIONS.md`。
2. **更新 `README.md`**:在 CLAUDE.md 那列的用途說明補上「含 grill-me 拷問模式」,並在注意事項提一句「嫌煩可整段刪掉」(維持模板可裁減的原則)。

## 二、範圍界線

- ✅ 可動:`CLAUDE.md`、`README.md`、`docs/`(BACKLOG、DECISIONS 於階段 3 照流程更新)。
- ❌ 這次不碰:`.claude/agents/rd.md`、`.claude/agents/tester.md`(拷問是 PM 對使用者的行為,與 RD/Tester 無關)、任何程式碼。
- ❌ 不做:獨立的 `.claude/skills/grill-me/` skill 檔。理由:PM 是主 agent、`CLAUDE.md` 每次對話自動載入,直接內建即可;拆成 skill 反而多一個載入時機的變數。若日後想給其他專案單獨引用,再另開需求拆出去。

## 三、驗收標準

1. `CLAUDE.md` 階段 1 含「grill-me 拷問模式」小節,涵蓋:雙軌啟動時機、五條拷問流程規則、四段收尾總結。
2. 觸發詞(grill me / 烤我 / 拷問我)明確寫入,且註明小需求不強制,由使用者決定。
3. 與既有七階段流程無矛盾:拷問只發生在階段 1,不改變階段 3 確認關卡與後續派工流程。
4. `README.md` 已同步更新。
5. 全程無任何程式碼與 agent 定義變更。

## 四、預見風險與對應處理

| 風險 | 處理 |
|---|---|
| 每個小需求都被拷問,使用者嫌煩 | 雙軌設計:預設只在「使用者點名」或「PM 判斷重大且使用者同意」時啟動 |
| 拷問無止盡,遲遲進不了階段 2 | 「一次一題 + 一條線追到底」本身收斂快;另給使用者「夠了」安全詞提前收尾 |
| `CLAUDE.md` 越寫越長,壓縮後 PM 漏看 | 收斂成一個小節、條列化;README 註明可整段刪除 |
| 拷問結論散在對話裡,換對話就忘 | 收尾四段總結進規劃書、關鍵取捨進 DECISIONS,照既有「拍板才落地」機制留痕 |
