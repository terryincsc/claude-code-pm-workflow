# 001 ─ 文件分家與 main 合流規則

- **日期**:2026-07-20
- **需求編號**:001
- **狀態**:🚧 進行中

---

## 一、這次要做什麼

1. **新增 `docs/DECISIONS.md`**(決策紀錄)
   - 只收「已拍板」的決策:一條一個編號,記「決定了什麼、為什麼、捨棄了哪些選項」。
   - 收納時機:PM 於階段 3 使用者說「確認」時,從規劃書摘錄關鍵取捨寫入。
   - 只增不改(決策被推翻時,不刪舊條目,新增一條並註明取代哪一條)。
2. **新增 `docs/BACKLOG.md`**(待辦與點子)
   - 每條帶狀態:`💡 想法(還沒討論)/ 📋 已排入(附規劃書編號)/ ✅ 已完成 / ❌ 不做(附原因)`。
   - 隨口點子記 💡,不單獨 commit,「搭便車」跟下一次文件 commit 一起進版。
3. **`docs/SYSTEM_STATUS.md` 瘦身回本業**
   - 只留:系統概觀、功能清單。
   - 原第三節「已知問題 / 待辦」改為「**已知 bug / 技術債**」(只描述現況;未來要做的事一律搬去 BACKLOG)。
   - 新增「**進行中任務**」小節:記錄目前進行中的規劃書編號與卡在哪個階段,強化中斷恢復。
4. **修改 `CLAUDE.md` 流程規則**
   - **拍板才落地**:討論過程不進版控;使用者說「確認」才 commit。
   - **文件先行**:階段 3 確認後,PM 立即 commit 規劃書 + DECISIONS + BACKLOG(標 📋),
     並盡快合回 `main`(遠端環境下由 PM 開 docs PR、提醒使用者 merge)。
   - **一需求兩 commit**:main 上每個需求只留兩筆——`docs: NNN 規劃書`(確認時)與
     `feat/fix: 成果`(收尾時,PR 一律 **squash merge**)。
   - **收尾定義變更**:階段 7 需成果 PR **merge 回 main 才算任務結束**,並更新 BACKLOG 為 ✅。
   - **開場恢復規則**:每次新對話開始,PM 先 `git fetch` 檢查有無未合併的 `claude/*` 分支
     或 open PR;有的話先讀取該分支上的規劃書/文件,向使用者確認「接續或放棄」,
     不憑 main 上的舊資料重新討論。
   - **RD 派工必讀清單**加入 `docs/DECISIONS.md`。
5. **同步更新 `README.md`** 的「內容物」表格與流程說明(加入新文件與合流規則)。

## 二、範圍界線

- ✅ 可動:`docs/`(DECISIONS、BACKLOG、SYSTEM_STATUS、plans)、`CLAUDE.md`、`README.md`。
- ❌ 這次不碰:`.claude/agents/rd.md`、`.claude/agents/tester.md`(派工時必讀文件由 PM
  在派工 prompt 中指定即可,不需改 agent 定義)、任何程式碼(本專案目前也沒有程式碼)。
- ❌ 不做:GitHub Actions 自動合併 docs PR(先走「PM 開 PR → 使用者手動 merge」,
  跑順了之後若嫌煩再另開需求加自動化)。

## 三、驗收標準

1. `docs/DECISIONS.md` 存在,含格式模板與收納規則說明,並已記入本次(001)的決策。
2. `docs/BACKLOG.md` 存在,含四種狀態的格式模板與「搭便車」規則說明。
3. `docs/SYSTEM_STATUS.md` 不再含「待辦」性質內容,新增「進行中任務」小節,
   第三節改為「已知 bug / 技術債」。
4. `CLAUDE.md` 含上述五條新規則(拍板才落地、文件先行、一需求兩 commit、
   merge 完才收尾、開場恢復),且與原七階段流程無矛盾。
5. `README.md` 內容物表格列出新文件。
6. 全程無任何程式碼變更。

## 四、預見風險與對應處理

| 風險 | 處理 |
|---|---|
| 文件變多,忘了更新其中一份導致互相矛盾 | 每份文件開頭註明「誰在什麼時機更新」;更新責任全部收在 PM 的階段 3 / 階段 7 檢查清單裡,不靠記憶 |
| 「文件先行合回 main」在遠端環境需使用者手動 merge,若使用者漏按,下個對話仍讀到舊 main | 開場恢復規則兜底:新對話一律先 fetch 檢查未合併分支/PR |
| CLAUDE.md 規則越寫越長,壓縮後 PM 漏看 | 新規則以條列收斂在既有章節內,不另開大段落 |
| 本專案是模板,規則改動會影響所有複製它的新專案 | README 註明各機制可依專案規模刪減(小專案可不用 BACKLOG) |

## 五、建議實作方向

- 全部為文件與規則改動,屬 PM 職掌,由 PM 直接執行,不派 RD、不需 Tester。
- 驗收方式:使用者依「三、驗收標準」逐條檢視文件內容。
- 完成後 commit 訊息:`docs: 001 文件分家與 main 合流規則`。
