### D001 ─ 專案知識拆成三份文件(2026-07-20,出自規劃書 001)
- **決定**:`SYSTEM_STATUS.md` 只記系統現況、`DECISIONS.md` 記已拍板決策、`BACKLOG.md` 記待辦與點子,三者分家。
- **原因**:全塞在 SYSTEM_STATUS 會變雜物間,「做過的、沒做的、只是聊過的」混在一起無法當事實來源。
- **捨棄的選項**:
  - 全部記在 SYSTEM_STATUS(雜、狀態不明);
  - Codex 式 8 份文件(AGENTS/PLAN/PROGRESS/MEMORY⋯):對本專案規模是過度設計,文件多了容易互相矛盾;
  - 記在 GitHub Issues:subagent 靠讀 repo 檔案了解系統,Issues 隔一層 API 且遠端環境偶有斷線,可靠性差。

### D002 ─ main 是唯一事實來源的載體;拍板才落地、一需求兩 commit(2026-07-20,出自規劃書 001)
- **決定**:
  - 新對話一律從 main 起步,所以拍板的文件必須盡快合回 main(「文件先行」:確認當下就 commit 規劃書 + 決策並開 docs PR)。
  - 討論過程不進版控,只有拍板的結晶才 commit。
  - 每個需求在 main 上只留兩筆:確認時的 `docs: NNN ⋯` 與收尾時 squash merge 的成果 commit。
- **原因**:成果留在未合併的 `claude/*` 分支上,新對話讀到的是舊 main,導致同一件事反覆討論。
- **捨棄的選項**:
  - docs PR 用 GitHub Actions 自動合併(先手動 merge 把流程跑順,嫌煩再另開需求,見 BACKLOG B002);
  - 讓分支長期存活累積多個需求(失憶與衝突的主因,一律快合快收)。
